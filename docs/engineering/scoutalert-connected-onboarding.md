## Identity and browser boundary

- `@repo/core/identity` owns shared sign-in, session access and expected failures. `@repo/adapters/identity` implements cryptography, PostgreSQL repositories and Redis abuse limits.
- Six-digit codes use Node cryptographic generation and a server-keyed HMAC bound to sign-in purpose, normalized email, initiating browser and generation. Codes are never stored as plaintext. Email addresses are trimmed and lowercased for account uniqueness.
- PostgreSQL owns challenge generations, five-attempt limits, ten-minute expiry, consumption and sessions. Row locks serialize resend and verification. Consumption, verified account upsert, session creation and prior-session revocation share one transaction.
- A replay of the same valid proof from the same browser within its expiry recovers the original live session after a lost response. It never creates a second session or restores a revoked one. Sessions expire after seven days and use keyed token digests in the database.
- Redis reserves destination (5/hour), browser (10/hour), network (50/hour) and verification-network (100/10 minutes) quotas atomically. Keys contain keyed identifiers and expire. Redis failure fails closed. Normal resend cooldown is 60 seconds; only the current generation can verify.
- Next.js sets host-only HttpOnly, SameSite=Lax cookies; production names use `__Host-` and Secure. Browser JSON never contains a session token. Every mutation requires an exact Origin and browser-bound keyed CSRF token. Account and code recovery comes from the server.
- The private API requires a shared host key and accepts browser/session/network context only from Next.js. Keep the API behind the web host/private edge in deployment. Client-supplied owner IDs and transport headers are never forwarded.
- `SCOUTALERT_WEB_ORIGIN` defines the browser origin. `SCOUTALERT_TRUST_PROXY=true` is allowed only behind an edge that overwrites `x-forwarded-for`; otherwise network requests share one conservative bucket. Development defaults favor localhost. This must be set deliberately for deployment.
- Error responses, SMTP client diagnostics and Observe request capture omit codes, credentials and personal brief payloads. SMTP acceptance is distinguished from inbox delivery. Uncertain submission is not retried automatically; the user can use an arrived code or request a newer generation after cooldown.

## Transactional activation

The activation API revalidates the confirmed search and schedule and obtains ownership from the durable session. An owner lock and `(owner_id, request_key)` uniqueness serialize retries. The request fingerprint detects reuse of a key with changed answers.

One transaction claims the approved brief, creates the scout and preferences, records granted or disabled consent with wording version `opportunity-alerts-v1`, stores a minimal unique outbox discovery intent, and saves the retry receipt. No SMTP, Redis or workflow submission occurs in this transaction. PostgreSQL foreign keys enforce ownership across drafts/scouts/preferences/consent/outbox records.

The browser keeps a non-authoritative activation retry key in session storage with an in-memory fallback. It restores editable drafts for seven days, clears remembered consent, and never stores email codes or session tokens. A completion URL includes an opaque scout ID; reload retrieves the owner-scoped saved receipt. A URL or browser approval marker alone cannot authenticate or save a scout.

## Live scouting execution

This section records the configured-source implementation. Broader source support must not be inferred from the word "live."

Connected sources are the **Figma** and **Remote** public Greenhouse job boards, plus **Freelancer** public buyer requests for fixed-price client projects and hourly services. Collection is shared across scouts and runs every five minutes. Freelancer coverage prioritises international remote work, excludes local-only/private/direct-hire requests and is a bounded rolling window, not the whole marketplace. Marketplace presence does not establish remote delivery or worldwide eligibility. The `services` scout category now retrieves buyer requests and participates in normal reconciliation; employment and contract-role scouts retain job-board retrieval. See [marketplace discovery](../../evaluations/marketplace-discovery/README.md) for limits and verification.

Start the isolated, persistent local execution service and worker in addition to web/API:

```sh
docker compose -p scoutalert-execution -f infrastructure/scouting.compose.yaml up -d
pnpm --filter @repo/core build
pnpm --filter @repo/adapters build
pnpm --filter @repo/workflows build
pnpm --filter worker build
pnpm --filter worker start
```

The worker reads `apps/api/.env` and optional `apps/worker/.env`; its defaults use local Temporal on 7233 and Mailpit on 1025. Temporal's development UI is on [localhost:8233](http://localhost:8233). A dedicated Docker volume retains workflow history across restarts. The volume initialization service changes ownership only on that isolated volume. This development server is not a production deployment.

`packages/workflows` contains deterministic finite definitions and small serializable activity contracts. `apps/worker` composes native Nest providers, Temporal clients and separately bounded task queues: source collection (2 concurrent activities), matching (4), public availability research (2), and delivery (1). Shared business behavior lives in `@repo/core/scouting` and `@repo/core/notifications`; all queries, persistence and provider access remain in adapters. Architecture checks also reject client, framework, repository and core execution imports in workflow definitions.

The PostgreSQL outbox relay claims 25 rows with `FOR UPDATE SKIP LOCKED` and one-minute leases. Workflow IDs derive from the persisted event UUID; Temporal rejects duplicate running or completed IDs. Only successful or duplicate admission acknowledges a current lease. A lost acknowledgement is retried after expiry without starting another logical workflow. Admission calls have a ten-second deadline. Native schedules create finite histories; no permanent per-scout timer workflow is introduced. New runs allow at most 32 bounded matching steps (older workflow histories retain 20 through native versioning) and have a twenty-minute execution timeout. Reconciliation closes orphaned runs, retries supported scouts after ten minutes, and processes up to ten fair batches of 500 per minute using bulk outbox inserts. These are bounds, not a production throughput claim.

The connector accepts only composition-owned board IDs, disables redirects, and limits each response to 15 seconds, 8 MB, 5,000 postings and bounded fields. It validates the full board count and every posting before publication, excluding prospect-only posts. Malformed or partial responses and outages cannot expire postings. Complete snapshots update public posting variants atomically; meaningful fingerprints increment versions and preserve normalized plaintext evidence/history. Unchanged postings reuse versions. Shared full-text documents use native PostgreSQL weighted `tsvector` and a partial GIN index. Detailed matching reads at most 200 candidates per run.

The initial policy requires a whole-word role phrase in the title's primary segment. Java is not JavaScript, and incidental department references do not count as the requested role. Explicit arrangement must-haves, opportunity category and unknown-information policies are enforced by the deterministic fallback. Board location or remote wording does not prove eligibility; pay amount/currency/period, experience and detailed fit remain unverified. Strict unknown/undisclosed-pay policies can therefore exclude every posting. This deterministic fallback is labelled **Potential match**, with reasons and uncertainties. Detailed assessment can now be enabled as described below.

Publication locks sources before scouts and checks current owner, active status, scout revision, latest run, posting revision/open status and thirty-minute evidence freshness. Changed evidence requires a new assessment. Dashboard reads repeat ownership/version/open/freshness checks and group contributions across scouts, showing at most twenty recent opportunities. These bounded lists are not exhaustive discovery counts. Refresh uses fresh Next server reads; only pending/searching pages poll, and hidden tabs pause polling.

## Evidence-linked AI assessment

This section and its recorded counts/costs describe specific historical runs. They are not independent discovery-quality or global-capacity evidence. The broader [discovery protocol](../../evaluations/discovery/README.md) adds acquisition recall, provider contribution, informal demand, source/time holdouts and cohort evaluation.

The local worker now supports shared posting extraction and private personal-fit assessment through the official OpenAI SDK. `packages/core/src/scouting/intelligence` owns the ports, evidence checks and publication rules; `packages/adapters/src/scouting/intelligence` owns Responses API access, runtime schemas and PostgreSQL task persistence. Nest composition constructs clients and binds the use case. API routes contain no model calls.

Configure `OPENAI_API_KEY` in ignored `apps/worker/.env`, run `node scripts/check-ai-assessment.mjs`, and enable `SCOUT_AI_ENABLED=true` after reviewing the results. Extraction and fit models are configured independently. The starting local configuration pins `gpt-5.4-mini-2026-03-17`, low reasoning, strict structured outputs and `store: false`. SDK retries are disabled. Each request has a 25-second deadline, a 60,000-byte input limit and a 4,000-output-token cap; oversized documents remain provisional instead of being silently truncated. The public source and confirmed brief are untrusted input. Source and brief passage IDs are resolved to original text by the adapter; unknown references, unsupported certainty and invented evidence are rejected before persistence. Source citations establish provenance, not semantic correctness or independent employer verification.

Each assessment covers role, work category, arrangement, applicant location, experience, work authorization and pay. Public extraction also retains sponsorship evidence. Results are `meets`, `conflicts` or `unknown`, with readable explanations and source/brief passages. Required arrangements and explicit role/category/location/authorization conflicts are enforced in core. Missing personal experience remains unknown. Residence never proves work authorization. Onboarding and scout editing collect optional countries, sponsorship needs and explicit confirmation. These are user-declared details, never an independent legal verification. Old scouts remain unknown until their owner supplies the details. Pay arithmetic only uses an unambiguous explicit base-pay range in a supported ISO currency and period. The initial normalizer recognizes forms such as `Base salary is USD 60,000 to 80,000 per year`; symbol-only, abbreviated, multiple regional ranges, unknown amounts and incompatible units remain unresolved. It does not fabricate exchange rates or working hours, and it does not override an unresolved applicability assessment.

`intelligence_tasks` caches extraction by posting identity/version/fingerprint and provider/model/prompt/schema configuration. Private fit additionally includes owner, scout version, the exact confirmed brief and extracted analysis. Canonical JSON prevents JSONB key-order changes from causing repeated calls. Cached reads require current owner and input versions. Eight previously unassessed candidates are frozen per logical discovery run; later runs progress through additional candidates, reusing earlier accepted **and rejected** assessments. The existing 200-candidate retrieval limit remains. Other candidates retain explicitly provisional results. One newly admitted model task runs per activity attempt; Temporal resumes subsequent steps from PostgreSQL without a source-wait timer after progress, using the native `scout-intelligence-progress-v1` workflow patch to preserve replay. It still waits when source evidence or a lease is unavailable. Reconciliation skips active runs until completion or the existing orphan timeout. No database transaction spans a model request. Cached accepted and rejected fit results are read in a bounded shared query before new task admission.

Fenced 45-second leases prevent simultaneous duplicate attempts. At most two provider calls are admitted concurrently, with a default shared ceiling of 50 reserved requests per UTC day. A failed or ambiguous attempt still consumes its allowance; retry requires a fifteen-minute cooldown, with two attempts maximum per exact task. Provider failures, invalid evidence and budget exhaustion preserve conservative behavior. Changes to posting/scout/configuration invalidate the corresponding cache. Completion and final recommendation publication recheck input revisions; late responses cannot replace current recommendations. `intelligence_attempts` records model, usage, duration and outcome without raw prompts or credentials. A model timeout can still incur provider charges; this implementation does not claim exactly-once paid inference.

Dashboard cards distinguish **AI assessed · Review details** from **Potential match**, identify which scout owns the displayed assessment, and expose every criterion with source passages. Scheduled digests use the same persisted reasons and unresolved questions after their existing consent/version checks. Unresolved questions remain visible. A separate public research worker checks exact posting availability and content continuity. Admitted matching candidates with missing public eligibility facts now receive bounded employer-policy research through approved career pages. General company slogans, customer EOR services and unclear role applicability cannot establish a match. The research and prompt rules below govern which evidence can support alerts.

The live synthetic smoke evaluation covers a suitable role, an explicit wrong-country exclusion and embedded malicious instructions. The successful five-call run used 5,049 input tokens and 2,174 output tokens in 19,514 ms total provider time. This measures the combined extraction/normalization/fit path on three synthetic cases; it is not a representative accuracy or recall benchmark. Earlier iterations failed numeric extraction checks, motivating explicit cited-range normalization. Provider/schema/model changes require rerunning evaluations. Broader multilingual, salary-format, seniority, applicant-location and adversarial datasets remain an adoption requirement.

The complete worker suite passed 31 checks; API unit and integration suites passed 7 and 12 checks respectively. `SCOUT_AI_LIVE_CHECK=1 node scripts/check-live-scouting.mjs` also passed through the real Next/API/Temporal/OpenAI/Mailpit path: two overlapping synthetic scouts, twenty grouped live opportunities including four AI-assessed recommendations, and one captured digest. The test revokes its own session and leaves the user’s browser session untouched. These bounded lists are not total match or recall measurements.

Run `SCOUTING_INTEGRATION=1 TEMPORAL_INTEGRATION=1 pnpm --filter worker test` for deterministic policy, isolated database, delivery and workflow recovery checks. The paid smoke command is separate and makes at most five calls, stopping at the first failed assertion. Its report is written to the OS temporary directory as `scoutalert-ai-evaluation.json`.

## Scheduled opportunity delivery

Daily and weekly digests follow confirmed timezone, local time, weekday and separate opportunity consent. Dashboard-only scouts are excluded. Native `Intl` timezone rules provide same-local-day catchup, skipped-hour recovery and one identity across repeated DST hours. A logical window is `(recipient owner, timezone, local date, delivery time)`; same-time daily/weekly scout contributions share one delivery. Different explicitly configured windows remain separate. Strong-match prompt alerts are optional and use the research and relevance gates below.

The ledger rechecks scout, preference and posting versions, current active/open/fresh state, email enablement and the latest consent event immediately before reserving submission. It records the actual grouped contents and contributing revisions under a unique recipient/window key. Item reservations prevent repeated alerts for the same source posting across later digests; an updated posting does not automatically re-alert in this initial policy. A fair persistent cursor scans fifty recipients at a time, with at most 100 contributions per owner, twenty unique postings per digest and a two-minute dispatch budget. SMTP runs after the transaction commits, with no database locks held over network I/O.

Provider acceptance, known rejection and ambiguity are distinct. Stable MIME Message-IDs aid tracing; they do not make SMTP idempotent. Crashes after reservation or lost SMTP acknowledgements become `unknown`, retain item reservations and are never blindly resent. Known rejection releases items for a later window. Uncertain submissions require an operator to inspect the ledger and Mailpit by that Message-ID before any deliberate repair. The dashboard displays held/rejected delivery notices. A production provider's idempotency, receipts and reconciliation API remain a separate adoption decision.

## Targeted availability research and prompt alerts

`ResearchAvailability` uses inward repository/source contracts. `PostgresAvailabilityRepository` seeds at most 100 missing public research tasks per claim and takes one due revision with `FOR UPDATE SKIP LOCKED`, a thirty-second lease and revision checks. The `scout-research-v1` Temporal schedule runs independently every minute, with at most four network checks per activity, a ninety-second activity timeout, two attempts, and non-overlapping scheduled runs. Source failures cannot delay the matching or delivery queues. Existing workflow histories do not change.

The source adapter calls the [Greenhouse retrieve-job endpoint](https://docs.greenhouse.io/job-board.html#retrieve-a-job) for composition-approved boards and numeric posting IDs. It never fetches a user-provided URL, follows redirects or sends a personal brief. Requests have a twelve-second deadline and one-megabyte response cap. Both collection and research use the same normalization and meaningful fingerprint. Unchanged available postings, unavailable/closed postings (404 or an elapsed explicit application deadline), changed details and unresolved provider/validation failures are distinct. Observations are shared by posting/version, retained in an append-only history, and rechecked after fifteen minutes. This is an availability/content check; wider employer-policy research remains platform work.

Prompt policy `isPromptMatch` now requires all seven criteria to be supported, including authorization, plus the `supported-criteria-v3` policy marker. The user must explicitly confirm countries and known sponsorship needs. Missing authorization or sponsorship evidence can remain in dashboard/digest review under user preferences, but never qualifies for a prompt. Unknown/conflicting criteria, legacy assessments, expired employer-policy evidence and absent/stale/changed/closed availability all block prompt delivery. Source availability must still match the exact posting revision and be less than fifteen minutes old. User declarations are not legal verification, and the UI/email do not claim they are.

The existing opt-in remains required. Users can choose local quiet-hour start/end in onboarding; older preferences default to 20:00–08:00 in their confirmed timezone. Equal start/end is rejected rather than silently disabling quiet hours. These hours govern prompts; daily/weekly digests follow their explicitly chosen schedule. Native IANA timezone conversion covers DST. Prompts are limited to **one posting per email and one attempted prompt per recipient in a rolling 24 hours**, across all scouts/timezones; rejected and ambiguous attempts consume that allowance conservatively. Saved preferences can be changed through the authenticated scout editor. Configurable volume thresholds remain future work.

The same `opportunity_deliveries` and `opportunity_delivery_items` ledger protects both delivery types. Under the recipient lock, preparation rechecks the current assessment, research observation, source/scout/preference revisions, current local window, latest consent and rolling volume. Concurrent prompts/digests cannot reserve the same posting. Current research rows are locked through reservation; network calls happen after commit. This closes the read-to-reservation race, not the unavoidable gap between SMTP submission and a later consent/source change. Prompt candidate grouping precedes digest grouping; an already emailed posting does not reappear in the digest. An unchanged assessment can therefore remain visible on the dashboard without triggering an alert.

The dashboard displays dated availability observations separately from AI fit. A live local run recorded four available postings through the scheduled research workflow. The isolated Mailpit test exercised a strong-match message, overlapping scout grouping and suppression of a subsequent digest of that same posting.

## Saved scout controls and recommendation feedback

The editor covers the complete confirmed brief and alert preferences, with inline application validation and no native validation popups. Pause/resume preserves the prior consent decision without recording a new grant; an explicit alert edit records its confirmed choice. Foreign or missing IDs return the same 404; stale versions return 409. Retries of a successful identical command return its original receipt, while altered payloads under the same key fail. Feedback updates are version-fenced and idempotent.

## Employer-policy research and stricter prompt verification

The next assessment stage follows public extraction and precedes private fit for the eight admitted candidates. It researches missing location, authorization and sponsorship facts using composition-approved Figma and Remote recruiting pages. It never sends a personal brief to the public source fetcher or lets a model choose a URL. At most two parallel eight-second HTML reads (two megabytes each, sixteen thousand extracted characters) precede one twenty-five-second structured model call. Oversized or incomplete pages are rejected. Redirects are refused. A finite source lease, six-hour source cache and fifteen-minute failure cooldown avoid duplicate page collection.

Research findings retain exact passages, source URL, document fingerprint, observation time, expiry, role applicability and resolved/conflicting/unresolved status. Explicit posting facts and contradictions take precedence; only missing facts can be supplemented.
