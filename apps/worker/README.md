# ScoutAlert worker

This Nest application context composes shared core use cases, repository/provider implementations and native Temporal clients. Eight task queues separate workflow orchestration, shared source collection, general-web discovery, learned-source monitoring, native social discovery, private matching, public availability research and recipient delivery. Activities bind to core use cases; they contain no queries or copied policy.

Start the local Temporal service with `docker compose -p scoutalert-execution -f infrastructure/scouting.compose.yaml up -d`. Build `@repo/core`, `@repo/adapters`, `@repo/workflows` and `worker`, then run `pnpm --filter worker start`. The worker reads `../api/.env` and optional `.env`; see `.env.example`. The execution UI is on localhost:8233. `dev` starts built JavaScript without Node watch mode; rebuild changed workspace packages and restart explicitly. Production startup is refused until a production email provider is composed.

`SCOUTING_INTEGRATION=1 TEMPORAL_INTEGRATION=1 pnpm --filter worker test` exercises isolated PostgreSQL transactions, Mailpit outcomes and a separate Temporal test namespace. Ordinary tests cover matching, schedule and connector policies without external services. Test namespaces have one-day history retention; local namespace deletion is a separate operator cleanup action.

The [connected onboarding and live scouting guide](../../docs/engineering/scoutalert-connected-onboarding.md) defines source coverage, schedules, limits, idempotency, uncertain delivery recovery and production adoption work.

AI assessment is opt-in with `SCOUT_AI_ENABLED=true` and `OPENAI_API_KEY` in the ignored local `.env`. Model settings and the default 50-request daily admission ceiling are in `.env.example`. Run `node scripts/check-ai-assessment.mjs` from the repository root for the separate five-call paid smoke evaluation. The worker uses shared versioned extraction, private fit caching, strict source citations, fenced leases, a bounded per-run candidate batch and conservative fallback. The operating guide documents supported pay formats, quality limits and remaining research work.

Daily allowances are operator configuration, validated against PostgreSQL counter capacity and exact microdollar arithmetic. The former 10,000-request/$100 validation caps no longer prevent a deliberately larger allowance. Changing configuration does not clear reservations or change per-attempt costs, concurrency, deadlines or provider quotas. Rebuild and restart to load it. Invalid-setting errors name fields without disclosing credentials.

## AI token limit and usage

Set `SCOUT_AI_GPT54_DAILY_TOKENS=250000` and `SCOUT_AI_GPT54_MINI_DAILY_TOKENS=2400000` in `apps/worker/.env` for independent daily allowances. These are also the defaults. Mini must have more capacity than GPT-5.4 when GPT-5.4 is enabled; both can be zero to disable generation. `SCOUT_AI_DAILY_TOKENS` remains an optional additional deployment ceiling: when omitted it is the sum of the two model allowances, and an existing explicit value remains enforced. Changing either model limit never lets it borrow from the other.

`SCOUT_AI_PLANNING_MODEL`, `SCOUT_AI_EXTRACTION_MODEL` and `SCOUT_AI_FIT_MODEL` default to `gpt-5.4-mini-2026-03-17`. Mini handles routine public planning, repeated action selection, source interpretation, structured extraction, employer research and ordinary private fit. The initial strategy accepts at most 2,000 serialized input bytes and 2,000 output tokens.

With `SCOUT_AI_EXPERT_ENABLED=true`, `SCOUT_AI_EXPERT_MODEL=gpt-5.4-2026-03-05` reviews selected completed mini assessments: cited conflicting facts, explicit conditional eligibility, and client briefs with multiple procurement requirements. Routing uses observable evidence rules rather than a model's confidence score. The first policy recognizes English restriction phrases; it is not exhaustive. A required review receives original source passages, provenance and the mini verdict, with a 24,000-byte serialized packet ceiling, medium reasoning and at most 4,000 output tokens. Omitted source context is marked incomplete and cannot justify upgrading an unknown/conflicting baseline to a positive criterion. Full-model review cannot fill missing facts or bypass the domain's eligibility, remote-work or evidence checks.

A stalled discovery case may use one full-model recovery decision after at least two completed searches and two source reviews have found no useful demand matching the stated remote requirement. It chooses only from the existing policy-approved actions, using a bounded evidence packet and at most 2,000 output tokens. Its durable phase allows at most one provider attempt per case. Missing mini reviews or exhausted mini capacity alone never trigger recovery.

`SCOUT_AI_AUDIT_PERCENT=5` selects a deterministic sample of both accepted and rejected private assessments; it is configurable from 0 to 10. This audits fit assessments, not every discarded raw search result. `SCOUT_AI_AUDIT_DAILY_TOKENS` defaults to 10% of the full-model limit: **25,000 audit tokens inside 250,000**, leaving **225,000** for required reviews and recovery. The two full-model allocations cannot borrow from each other. Setting the audit percentage to zero disables sampling; set its token allocation to zero too if that capacity should return to required reviews. Audit counts vary with volume and available capacity; the percentage is not a quality guarantee.

The current local activation explicitly sets `SCOUT_AI_AUDIT_DAILY_TOKENS=40000`, allocating 40,000 audit and 210,000 standard tokens inside the unchanged 250,000-token full-model cap. This operator override does not change the default 10% allocation or increase mini/the combined ceiling. See the [completed audit tests](../../evaluations/discovery/expert-audit-final-summary-2026-10-29.json).

Required reviews remain unpublished if the review is unavailable or invalid. Optional audit failures retain the validated mini baseline. Expert reviews have one attempt per immutable source/brief/baseline and are cached privately by owner and scout version; terminal failures do not monopolize future candidate batches. Failed recovery returns to the ordinary bounded planner. No stage switches models to evade a token ceiling. The policy has boundary and live synthetic smoke checks; independent comparative accuracy still requires a representative, labelled mini-versus-full evaluation.

Expert fit requests have a 40-second response deadline inside their 55-second durable lease, leaving time to settle tokens and persist the result. The expanded live check found several failures near the previous 25-second deadline; a subsequent valid review took 28.75 seconds. The longer deadline does not add retries or release reservations for earlier unknown outcomes.

`expert-fit-v2` references repeated exact source and brief quotations by passage ID while retaining the original passages, provenance and completeness markers. Unmatched quotations remain literal baseline claims. This keeps repeated citations from exhausting the existing 24,000-byte packet ceiling without dropping source conditions. Both fit prompts distinguish employer preferences from mandatory restrictions and leave missing evidence of a required skill unknown. `node scripts/evaluation/check-discovery-regressions-live.mjs <new-receipt-path>` rechecks the two recorded live failures with mini and the expert, using the shared daily ledger plus a stricter 20,000-token invocation ceiling; it does not refresh availability or publish the recorded cases.

PeoplePerHour's `peopleperhour-public-html-v4` parser records explicit non-open platform states from complete primary buyer sections. `public-document-v13` invalidates older captures, and `lead-evidence-v6` interprets paused/awarded/archived requests as closed. The domain publication gate also rejects parser-confirmed closure independently of the model verdict. A newly reviewed closed capture withdraws the earlier public posting; open status alone never establishes personal fit.

`SCOUT_AI_MAX_OUTPUT_TOKENS=4000` bounds response size independently. It accepts 16–4,000 tokens; planning keeps its lower 2,000-token maximum. Existing request and USD limits still apply, and low response limits can leave structured answers incomplete. Standard-tier cost estimates cover [GPT-5.4](https://developers.openai.com/api/docs/models/gpt-5.4) and [GPT-5.4 mini](https://developers.openai.com/api/docs/models/gpt-5.4-mini), including cached input; estimates are not invoices.

Each daily total includes input plus output tokens across its model's stages, shared by every worker using this database. The aliases `gpt-5.4` and `gpt-5.4-mini` share their respective pinned snapshot's allowance; an unreviewed model version is rejected. Cached input counts once as input; reasoning counts within output. The day resets at midnight UTC (01:00 in Africa/Lagos); calls crossing midnight belong to their admission day. A restart, model alias change or configuration change does not reset usage.

Before generation, the native [OpenAI input-token endpoint](https://developers.openai.com/api/docs/guides/token-counting) counts the actual text, instructions and output schema. PostgreSQL locks the admission day, checks the selected family's existing reservations and atomically reserves that input count plus maximum output against both ceilings. If the whole reservation does not fit, no generation is sent. The configured output limit is sent to OpenAI, which includes reasoning and other non-visible output in that limit. Counts and response bounds depend on the provider honoring this API contract; any unexpectedly higher reported usage is recorded truthfully and reduces subsequent capacity.

Actual usage is settled before schema/evidence validation, including incomplete or unusable answers. Unused reservation is released only after valid usage is received. Missing usage, transport failures and abandoned calls retain their full reservation for that admission day; they are never assumed free. Counting/database failures stop generation. Existing task cooldowns and conservative fallback still apply; blocked attempts can retain the existing request/USD reservation even though no model generation occurred. No prompts, profile contents, API keys or response text are stored in the token ledger.

After rebuilding core, adapters and worker and applying migrations through `20261029-selective-model-review`, restart the worker to activate enforcement. Independent family limits reuse the existing usage records. The selective-review migration adds reservation purpose and a private review-to-baseline link, preserving earlier usage as standard work without resetting counters. Run `pnpm --filter worker ai:usage` to read the overall and per-model input/output totals, cached input subset, actual tokens used, retained reservations, remaining allowance and unknown outcomes. The report includes protected standard/audit allocations. Per-model remaining capacity also respects any stricter global ceiling. This command does not call a model. Tracking starts when the guarded worker is activated. Stop old worker instances during rollout so all running workers use the guard and the same configured limits.

`scripts/evaluation/check-live-scout-quality.mjs` shares the configured worker database's token ledger and limits, while keeping scenario records in a disposable test schema. Its receipt attributes its own generation attempts separately from concurrent worker activity. `--without-ai` does not open or spend from this token ledger. `scripts/evaluation/check-selective-review.mjs <new-receipt-path>` also shares this ledger for three live expert calls on authored source/baseline cases, with zero mini generations or emails. It tests correction and evidence boundaries, not fresh discovery or comparative quality. Historical telemetry, other standalone evaluation scripts and other applications using the same API key remain outside this ledger; do not run those paid evaluations when enforcing this shared allowance.

`node scripts/evaluation/check-expert-review-live.mjs <new-receipt-path>` exercises eleven expert fit reviews and three recovery decisions through the durable production use cases. It replays authored or recorded mini outputs with no mini generations, uses synthetic accounts in a disposable schema, and checks that cache replay spends nothing. An additional 80,000-token test ceiling sits below the deployment/model/audit ceilings. `--only=case-name,another-case` selects a targeted retest and `--token-ceiling=28248` can further reduce that invocation's ceiling. The local test ceiling restarts per invocation, so a targeted retest must be limited to the original batch ceiling minus its already accounted usage; the shared daily ledger never resets. Existing unknown reservations remain charged. See the [expanded expert test results](../../evaluations/discovery/README.md#expanded-gpt-54-live-checks--29-october).

New remote project/service cases use `client-demand-v8`: remote-focused and broad buyer queries, individual-source hints, and bounded query recovery when reviewed briefs leave remote work unresolved. Remote directory wording and search snippets never establish eligibility. The current PeoplePerHour reader retains explicit expired/paused/archived evidence, including pages that canonicalize to their category; open listings retain strict project identity checks. `--without-ai --planning-fallback` exercises the current unavailable-planner route with zero model calls. See the [remote-discovery receipts and pending AI validation](../../evaluations/discovery/README.md#remote-buyer-discovery-and-daily-cap-validation--29-october).

Availability research uses allowlisted employer ATS endpoints, shared posting/version leases, fifteen-minute reuse and independent finite Temporal runs. Prompt alerts require the strict relevance/availability policy, explicit opt-in, local quiet hours and a one-per-recipient rolling 24-hour limit. Prompt and digest delivery share the same item ledger. Apply migrations before starting the new worker.

For the expanded nine-case synthetic assessment evaluation, run `SCOUT_AI_EXTENDED_CHECK=1 node scripts/check-ai-assessment.mjs` (up to seventeen paid requests, separate from the worker allowance). It is a regression suite, not a representative quality benchmark.

Freelancer public fixed-price projects and hourly service requests are now collected through a bounded rolling feed. Individual availability is checked before any client-request email. Relevant feedback queues a refresh and adjusts private ranking without changing evidence or the confirmed brief. See [source coverage and verification](../../evaluations/marketplace-discovery/README.md).

## Target internet discovery workloads

The [discovery architecture](../../docs/architecture/scoutalert-discovery-architecture.md) expands execution into search I/O, streams/collection, fetch/render, extraction/indexing, personal matching, research, source expansion and delivery pools. The current eight queues and local concurrency values describe today's implementation; they are not the target's maximum capacity or proof of global scale.

Scout Planner, Deep Discovery Agent, Evidence Research Agent and Source Expansion Agent are distinct application responsibilities. The host binds their core use cases and provider/repository adapters; it does not duplicate planning, source-admission, matching or consent rules. The initial Serper adapter and finite query planner are implemented, live-tested and enabled locally under shared budget caps. Native X recent search and lookup are implemented behind explicit configuration; recent search, refresh and bounded context lookup are live locally; independently measured social quality remains open. The broader agent roles remain incomplete.

Shared monitoring and reserved exploration run independently of whether a personal index read found enough matches. Provider quotas, source limits, fair scheduling, durable budgets and input revisions constrain execution. Ingestion progress cannot advance beyond accepted durable work; gaps and partial results remain visible. See the [roadmap](../../docs/engineering/scoutalert-delivery-roadmap.md) and [DACC gates](../../docs/engineering/scoutalert-discovery-acceptance.md) before expanding live worker behavior.

## General web discovery

The worker now includes an opt-in Serper search adapter and a separate `scout-web-discovery-v1` pool. It persists reusable public queries, provisional leads, source evidence and bounded request reservations. A subsequent review activity classifies public demand and extracts cited source facts; it shares the existing AI request/cost/concurrency budget with private matching. Budget deferrals are visible in discovery activity. Configure `apps/worker/.env.example` settings only after following the [implementation and verification notes](../../docs/engineering/scoutalert-web-discovery.md). The provider is disabled by default; choosing Serper does not establish live access.

`dev` runs without Node watch mode because the installed Node/Temporal combination crashes before polling when watch mode is enabled. Rebuild and restart after changes. Workflow threading and timeouts stay enabled; no dependency code is patched.

New discovery cases use a bounded adaptive policy after the initial portfolio: observed source/application links, promising results, productive next pages and demand-query refinements. The existing document/daily budgets and four-minute deadline apply to all follow-ups. Historical fixed plans keep their original behavior. See the implementation guide for the decision ledger, live smoke report and model-guided planning and remaining coverage work. Raising `SCOUT_AI_DAILY_REQUESTS` does not raise the independent `SCOUT_AI_DAILY_USD` reservation ceiling.

AI-enabled new cases use `public-intent-v3`: shared structured strategy, source review between exploration actions, and bounded model selection from permitted actions. Public/private boundaries and the global AI ledger apply to planning too. Captured linked application/employer pages can support research without another unbudgeted fetch. Apply `20261001-worldwide-strategy-reasoning` before restarting. Historical plans remain frozen; source-only review completion leaves unchecked snippets explicitly unverified. See the implementation guide for live positive/negative trials and the diagnostic baseline comparison.

## Continuous source monitoring

`scout-source-monitoring-v1` runs a separate one-minute native schedule with finite histories. Complete source reviews can enroll shared URLs; changed captures and a bounded observed-link frontier feed current private scout runs through the outbox. `SCOUT_MONITOR_ENABLED` defaults to true when web discovery is enabled. `SCOUT_MONITOR_MAX_SOURCES` defaults to 32 per current scout. Both monitoring migrations must run before loading this worker. Document and AI limits remain shared with the existing pipeline; disabling monitoring does not erase its ledger. See [behavior and verification](../../docs/engineering/scoutalert-web-discovery.md#continuous-source-monitoring--2-october-2026).

## Native X discovery

`scout-social-discovery-v1` advances shared recent-search windows and post refreshes with a separate UTC-day request/reservation budget. Apply `20261002-x-discovery`, `20261003-x-context` and `20261003-yield-scheduling` before startup. Context follows up to six source-declared related posts across two levels, sharing requests and retaining separate attribution; edits, expiry and deletion invalidate dependent assessments. Native reads require `SCOUT_X_ENABLED=true` and `X_BEARER_TOKEN`; default access is disabled. Existing post-expiry maintenance continues without API access. See [configuration, source lifecycle and verification](../../docs/engineering/scoutalert-native-social-discovery.md).

When AI admission becomes available, maintenance requeues unfinished native reviews deferred by a budget or elapsed review window. Retained captures can be reviewed without another X read; their original observation timestamps still govern personal matching and delivery freshness. Paused/edited scouts and expired/inaccessible sources remain excluded. New native batches wait for active public reviews instead of superseding them.

## Discovery scheduling

Public query/source measurements now guide approved query order and source-check selection. X uses adaptive revisit intervals and daily pacing after three startup requests, while preserving oldest-due turns, exact cursors and existing budget/freshness guards. Apply `20261003-yield-scheduling` before restarting the rebuilt worker. See [policy, measurement semantics and verification](../../docs/engineering/scoutalert-discovery-scheduling.md). The aggregate report is `node scripts/evaluation/report-discovery-performance.mjs --write`; it does not supply independent relevance judgments.
